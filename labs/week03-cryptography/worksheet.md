## Part 2 — Lecture Questions

1. Distinguish hashing, encryption, and encoding — and give one job each is the wrong tool for.
Using Each for the Wrong Job

Hashing: The wrong tool for sending secret messages intended to be read by the recipient.

Reason: Hashing is a one-way function. Once data is processed, the hash value cannot be converted back into the original text; the original data is effectively lost.

Encryption: The wrong tool for storing user passwords.

Reason: Although it may appear secure, encryption is reversible (two-way). If the server or the encryption key is compromised, hackers can immediately decrypt everyone's passwords into plaintext. This task requires a one-way salted hash (e.g., bcrypt, Argon2) instead.

Encoding: The wrong tool for security or data obfuscation.

Reason: Encoding involves no data protection mechanism and uses no secret key. Anyone who recognizes the format (e.g., Base64) can immediately reverse the process; therefore, it cannot be used to prevent unauthorized access to data.

2. Why is a fast hash like MD5/SHA-1 a bad choice for storing passwords, and what should be used instead?

Brute-Force & Hardware Acceleration: Modern GPUs, ASICs, and dedicated cracking rigs can calculate billions (or trillions) of MD5/SHA-1 hashes per second. If an attacker dumps your database, they can brute-force 8-character complex passwords in a matter of minutes or hours.

Precomputed Attacks (Rainbow Tables): Fast hashes without built-in per-user salts are vulnerable to lookup tables containing billions of precomputed hashes of common passwords and wordlists.

Cryptographic Vulnerabilities: Both MD5 and SHA-1 suffer from well-documented collision vulnerabilities, rendering them completely broken for cryptographic security.

3. What is a salt, what attack does it defeat, and why must it be unique per password?

What is a Salt?

A "Salt" is a random string of data (numbers or text) generated by a secure system (CSPRNG) and appended to or combined with a user's password before it is processed by a hash function (e.g., `Hash(Password + Salt)`). This Salt is stored alongside the hash value in the database in plain view (it does not need to be kept secret).

Attacks Prevented by Salts

Rainbow Table Attacks: Hackers often pre-calculate hashes for common words and store them in large tables for comparison. When a highly random Salt is used, the resulting hash will not match any entry in these pre-computed tables, rendering Rainbow Tables ineffective.

Bulk / Batch Cracking: "Shotgun-style" database attacks aimed at cracking multiple user passwords simultaneously in a single pass become impossible. Hackers can no longer compute a single hash and compare it against the entire system's user base.

Why Must Salts Be Unique per Password?

If a system uses the same Salt globally (Global Salt) or reuses Salts:

Identical passwords yield identical hashes: If User A and User B both set their password to "Password123":

Without Salt or with reused Salt: Their hashes would look exactly the same. Hackers would immediately know they share the same password; if one person's password is cracked, the other is instantly compromised.

With Unique Salt: Even if the passwords are identical, the resulting hashes will be completely different, making it impossible to detect password similarities from the outside.

Forces hackers to compute hashes individually: Since each account has its own unique Salt... Hackers would need to execute a brute-force attack individually for each person—a one-to-one process—causing the time and cost required to compromise the entire database to multiply in direct proportion to the number of users (e.g., with one million users, the cost increases a million-fold).

4. Why does AES-ECB leak structure, and what does an authenticated mode like AES-GCM add?
ECB (Electronic Codebook) is the simplest block cipher mode; it divides data into equal-sized blocks (16 bytes for AES) and encrypts each block independently using the same key.

Deterministic Encryption: If plaintext blocks are identical, the resulting ciphertext will always be the same.

Patterns are not hidden: Most real-world data contains repetitive patterns—such as identical pixel colors in an image or structural fields in files/protocols (e.g., JSON, XML)—meaning the resulting ciphertext retains the original outline or structure.

A classic example is the "ECB Penguin": when the Tux penguin image is encrypted using ECB mode, the color details change, but the penguin's outline and shape remain clearly visible.

What AES-GCM adds:

AES-GCM (Galois/Counter Mode) is classified as an AEAD (Authenticated Encryption with Associated Data) scheme. It addresses data leakage issues and adds three critical security features:

1.Randomness via Nonce/IV (Solving the Structure Leakage Problem):

GCM utilizes Counter Mode (CTR Mode) combined with an Initialization Vector (IV/Nonce) that is randomly generated for every operation.

Identical data blocks yield completely different ciphertext results each time, ensuring no original patterns or structures remain visible.

2.Data Integrity & Authenticity (Preventing Data Tampering):

Basic modes (such as ECB or CBC) only ensure confidentiality; they are vulnerable to attacks like "bit-flipping," where the secret content could be altered without the system detecting it.

GCM always generates an Authentication Tag (MAC); if even a single bit of data is altered... The decryption process immediately flags errors and rejects the data.

3.Support for Associated Data (AAD):

It can verify the integrity of header information or metadata that must remain in plaintext (such as port numbers or IP addresses) without encrypting those specific parts.

4.High Speed ​​and Performance:

GCM computations support parallel processing on modern hardware, making it significantly faster than chaining modes like CBC.

5. What's the difference between `random` and a CSPRNG (e.g. `secrets`), and where does it matter?
Key Differences

`random` (Standard PRNG): Designed for speed and data simulation (often using the Mersenne Twister algorithm). It is **not** cryptographically secure because it is predictable; if a hacker observes a sufficient number of outputs (e.g., 624 values ​​in Python), they can reverse-engineer the sequence to determine all future values.

CSPRNG (e.g., `secrets`): Stands for Cryptographically Secure Pseudo-Random Number Generator. It draws entropy (random variance) directly from the operating system. It is designed to be mathematically unpredictable; even if a hacker knows all previous values, they cannot predict the next one.

Critical Risks of Choosing the Wrong One (Where it matters)

Using standard `random` for security-sensitive tasks creates critical vulnerabilities in the following scenarios:

Session IDs and CSRF Tokens: Hackers can predict token values ​​in advance to perform session hijacking and impersonate other users.

Password Reset Tokens / Magic Links: Hackers can trigger their own password reset to calculate the sequence and then guess the reset token for an administrator account.

Cryptographic Keys, Nonces, and Salts: If used to generate IVs/Nonces for encryption (like AES-GCM) resulting in collisions, or to generate secret keys, the entire encryption system can be immediately compromised.

OTP / Verification Codes: Verification codes can be guessed without waiting for the actual transmission.
